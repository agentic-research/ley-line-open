Section: Security

- **The read-only `query` op reads only listed virtual-table modules** (bead `ley-line-open-a9be1f`).
  The authorizer allowed a read of any table name, so whichever table-valued functions and eponymous virtual tables the build and every `sqlite3_auto_extension` registered were reachable, and a module added later with host reach (`fsdir`, `zipfile`, `csv`) would have been allowed with no failing test. A read is now allowed only for a plain table or view of the `main` schema, the modules `json_each`, `json_tree`, `dbstat` and sqlite-vec's `vec_each`, and the `pragma_` tables of the allowed schema pragmas. Every other module, including a virtual table in the schema (FTS, R-tree) and `sqlite_temp_master`, is refused when the statement is prepared, as `denied_action` with action `read` (or `pragma` for a `pragma_` table) and the name as `subject`, over the control socket and MCP alike. Modules are told from tables by reading `sqlite_schema` and `pragma_module_list` on the reader before the authorizer is installed, never from the SQL text, and a test fails when the build gains a module that is neither allowed nor denied by name. An FTS or R-tree table is now refused the same way on every reader, whatever the reader ran before (bead `ley-line-open-07237c`). A refusal after a leading `;` or NUL names the statement's keyword (`vacuum`), and a denial after rows were produced is pinned to return the refusal and no rows over both transports (bead `ley-line-open-a9d50a`).
