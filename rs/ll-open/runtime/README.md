# leyline-runtime

Capability-resolved execution lifecycle and isolation backends (`execution/v1`). Product policy is resolved before this crate is called — it accepts content identities and guest-relative names; backend-only host paths are introduced behind trusted resolver boundaries.

## What's here

- **`authorization`** — `AuthorizedExecution`, `EvidenceVerifier` (+ `CasDsseEvidenceVerifier`, `MetadataOnlyEvidenceVerifier`, `RejectUnverifiedEvidence`), `SignedGrant`/`GrantSignature`, `SchemaIntent` — the trust boundary between an execution request and permission to run it. `CasDsseEvidenceVerifier` reports each refusal as an `EvidenceRejection` (`grant-unsigned`, `untrusted-signer`, `signature-invalid`, `evidence-missing`, `evidence-integrity`, …): an `ExecutionError` whose `detail` begins with the reason's stable token, recovered with `EvidenceRejection::of`.
- **`cas_evidence`** — what `leyline execution-daemon --evidence-store DIR --trust-key FILE` installs (bead `ley-line-open-410921`): `CasEvidenceStore`, an `EvidenceStore` over `leyline-core`'s `FsBlobStore` addressed by evidence digests (`blake3-256:<hex>` over the exact envelope bytes); `parse_trust_key`/`load_trust_keys` for operator key files (64 hex characters or a canonical RFC 8410 PEM `PUBLIC KEY`), each named by its ADR-012 canonical kid (SHA-256 over SPKI DER, a key's name, never a content address); and `operator_verifier`, which refuses an empty, malformed or repeated key set and a missing store directory.
- **`artifacts::oci`** — turns a digest-pinned OCI image into the content-addressed rootfs the backends consume (bead `ley-line-open-7736ab`); see "Container images" below.
- **`backends`** — isolation backend implementations: `native` (process), `native_backend`, `libkrun` (microVM). `Backend` is the trait each implements; `BackendCapabilities` / `BackendClass` describe what a backend can enforce.
- **`backends::libkrun`** — the microVM tier. `KrunWorkerBackend` supervises the `leyline-krun-worker` binary, which the unpublished [`leyline-krun-worker`](../krun-worker/) crate builds (bead `ley-line-open-395e43`). That crate is the only one that links libkrun, from [`third_party/libkrun`](../../../third_party/README.md) (upstream v1.19.6 plus LLO's patches, ADR-0044); this crate has no libkrun dependency and stays publishable. `worker::prepare` is everything the worker does before the VMM: it checks the share and the inherited descriptors, compiles the plan, materializes the ephemeral rootfs and applies the confinement manifest, and returns a `PreparedRun` (the VM's `KrunConfig`, the share socket, the applied manifest's digest and the readiness event). The worker crate builds the VM from it through `api::LinkedKrunApi`, attaches the share as a `DynFileSystem` and enters the VM.
- **`backends::libkrun::share`** — a run's workspace as the guest's working tree (ADR-0044 phase C, bead `ley-line-open-f210c2`). A run whose RunGrant carries a `WorkspaceGrant` reaches the backend with `ExecutionRequest.workspaces` (carried by the resolver; the service refuses one that changes them). `KrunWorkerBackend::with_workspace_shares` takes the embedder's `WorkspaceShares`; for the run's one granted workspace the backend opens an `FsService` before it spawns the worker, passes one end of a socket pair as `--workspace-share-fd`, and `serve`s the other end. The worker checks the descriptor is a socket matching the grant, attaches `ShareFs(RemoteFs)` (`leyline-krun-worker`; libkrun's `DynFileSystem` transcribing each FUSE request onto the wire) under tag `work`, and sets `KRUN_VIRTIOFS_MOUNTS=work:/work` and the working directory `/work`: the guest init (libkrun patch `0005`) mounts the share before the workload runs. No provider, two workspaces, or a provider refusal refuses the run before anything is spawned. The share descriptor is a channel the worker holds outside its `confinement/v1` manifest (nono confines what the process may open, not what it inherits open), so it is declared instead (bead `ley-line-open-b83347`): `worker::declared_descriptors` derives, from the grant and the descriptor number, the descriptors a worker holds beyond its standard streams (the share for a run granted a workspace, none otherwise); the backend spawns the worker through `worker::inherit_only`, which marks every other descriptor it holds close-on-exec in the child (a descriptor the daemon inherited open from its own parent included); the worker lists its open descriptors (`/dev/fd`) before it reads the rootfs and refuses to start holding any it does not declare (`IdentityPolicyMismatch`, naming the descriptors); its readiness event carries the declaration (`inherited`), which the backend refuses unless it equals what it handed the worker; and `BackendRun.channels` reaches the receipt, whose `backend.evidence` is the digest of a `BackendEvidenceDocument` (`application/vnd.leyline.execution.backend-evidence+json`, execution/v1 README "Backend evidence") naming the backend and each `WorkerChannel::WorkspaceShare {workspace, graphRoot}`. `WorkspaceGrant.expectedGeneration` is ADR-0041 S1's commit `seq`, which no store records yet, so the store's share refuses a grant whose `expectedGeneration` is nonzero (bead `ley-line-open-39abfa`); the share is pinned by the `graphRoot` check. The wire is one frame per request and reply: two little-endian `u32` lengths, a Cap'n Proto header (`leyline-public-schema`'s `capnp/share.capnp`, bead `ley-line-open-39d3a4`), and READ/WRITE bytes as raw payload. `leyline-storefs`'s `DaemonShares` is the store-backed provider; `rs/ll-open/cli/tests/agent_in_guest.rs` runs an agent in a guest against it (`task runtime:test`, with `LEYLINE_LIBKRUNFW_PATH` and `LEYLINE_GUEST_TOOLS` from `tools/guest_tools.sh`).

## Container images

An OCI image is a build input and distribution format here, not an isolation boundary. libkrun (or, on the native tier, nono) is the boundary; the image only supplies the files a run's rootfs holds. Docker, Buildah, Podman, skopeo and crane are optional ingestion adapters: any of them may write the [OCI image layout](https://github.com/opencontainers/image-spec/blob/v1.1.0/image-layout.md) an import reads, and none is needed to import or run it. Execution never contacts a container daemon and never shells out to krunvm.

`artifacts::oci::import_oci_layout`, and the `leyline rootfs import-oci --layout DIR --image sha256:<hex> --cas-root DIR [--symlinks refuse|resolve]` command over it, publish the image's root filesystem as `<cas-root>/<blake3 hex>/` with its `rootfs.manifest.json`. The digest is the existing rootfs identity: BLAKE3 over the manifest's exact bytes, which `DirectoryRootfsResolver` verifies on every resolve, and the `rootfs` an execution catalog entry names. The command prints one JSON document: `rootfs` (that digest, as `{"algorithm":"blake3-256","value":…}`), `image` (the pinned reference, the manifest and config digests, and the platform: OCI SHA-256 provenance, never compared with the rootfs digest), counts, and `imageConfig` (the config's entrypoint, cmd, env, working directory and user, advisory for whoever writes the catalog).

The import's contract, each clause tested in [`tests/oci_rootfs.rs`](tests/oci_rootfs.rs):

| Clause | Behavior |
| --- | --- |
| Pinned input | `sha256:<hex>` or `name@sha256:<hex>` of an index or manifest. A tag is refused; `index.json`, whose tags are mutable, is never read. |
| Authentication | Every blob must be a regular file, hash to its descriptor digest and match its size before it is parsed; layers are verified into owner-only staging and parsed from there. Each layer's whole uncompressed stream (every gzip member) must hash to its config `diff_id`. |
| Bounds | `max_rootfs_bytes` (16 GiB from the CLI) bounds the decompressed bytes of all layers, headers and long-name metadata included, and separately the bytes written. Paths and link targets over 4096 bytes are refused. |
| Platform | An index yields the one entry for the requested platform (`arm64` without a variant is `arm64/v8`); none or several is an error. The config must agree. The CLI always requests this host's Linux platform, the only one libkrun can boot. |
| Layers | Applied in order to an in-memory tree. `.wh.<name>` and `.wh..wh..opq` remove lower-layer entries only. Gzip and uncompressed layers are read; zstd is refused. |
| Modes | A file's permission bits are kept. Setuid, setgid and sticky bits are cleared and counted. A file its owner cannot read is refused (the manifest could not be verified). Directory modes, empty directories, ownership, timestamps and extended attributes are not in rootfs manifest v1, so none is carried: directories are written `0755` only where a file needs one, so one digest names one tree on disk. The guest init creates `/dev`, `/proc`, `/sys` and `/tmp` itself. |
| Links | Rootfs manifest v1 has no link entries. `--symlinks refuse` (the default) names the first link; `resolve` replaces each with a copy of the file or directory it resolves to inside the image (absolute targets mean the image root). Dangling links, loops, a `..` above the image root and a directory link containing itself are refused. Hard links become a second regular file. |
| Paths | Absolute paths, `..`, entries under a regular file or through a link, device nodes, FIFOs and an image-root `rootfs.manifest.json` are refused. No image path reaches the host filesystem until the finished tree is written beneath staging inside the CAS root; extracted contents wait there under their BLAKE3 names. |
| Identity | Files are listed in path order with fixed field order, so the same image content has the same rootfs digest whatever its archive order, host or run. |
| Publication | The staged tree is verified against its own manifest and renamed into place. An existing entry is reused only if its files verify and its directories are exactly the ones the import wrote, all `0755`; it is never replaced. Files are not fsynced before the rename. The resolver itself still checks files only (bead `ley-line-open-38ff59`). |

Where each kind of test runs: the importer, the resolver and the conformance rows that need no guest run anywhere, including in a container; a real guest needs a hypervisor, so macOS Hypervisor.framework tests run on a macOS host and Linux KVM tests on a host or runner given `/dev/kvm` (the libkrun column of the conformance matrix, below). Booting an imported rootfs in a guest is not yet part of the suite.

## Features

This crate has no cargo features. The `vmm` feature it had until bead `ley-line-open-395e43` is removed: libkrun and the `leyline-krun-worker` binary are the `leyline-krun-worker` crate's. Building that crate compiles libkrun's Linux guest init with `$CC_LINUX`, which the repository's `.cargo/config.toml` points at `tools/krun_init_cc.sh` (the host `cc` on Linux, `zig cc` elsewhere).

- At run time the worker loads one library, libkrunfw (the guest kernel), at `krun_create_ctx`, after its sandbox is applied: grant it with `--runtime-file` and put its directory on the loader path.
- **`confinement`** — ADR-0035's single-declaration manifest: one `cloister/confinement/v1` value from which the applied `nono::CapabilitySet`, the `confinementDigest`, and the digest a backend commits to are all projections, so they cannot drift relative to each other. (Before this existed, `build_process_capabilities` compiled a hardcoded policy with no relationship to the grant's named digest — PR #312 finding 2.)
- **`service`** — `ExecutionService` / `ExecutionResolver`, the orchestration layer driving a request through authorization → backend selection → run.
- **`transport`** — wire-facing types for the execution surface.
- **`CatalogBuilder` / `CatalogResolver`** (`catalog`, private module, re-exported) — resolves declared capabilities against what a backend actually offers.
- **`RunRecord` / `RunState` / `RunReceiptData` / `RunEventRecord`** (`model`, private module, re-exported) — the execution lifecycle's data model, including the DSSE-attestable receipt (see `leyline-envelope`).

## Used by

- **`leyline-cli-lib`** — hosts the `llo_execution_*` daemon ops (`capabilities`, `provision`, `status`, `start`, `inspect`, `cancel`, `collect`, `cleanup`).
- **`leyline-cli`**.
- **cloister** (external, `rs/crates/host-runtime`) — depends on this crate directly via git-rev pin, gated behind its own `llo-execution` feature (`dep:leyline-runtime`), because `leyline-runtime` pulls in `nono` unconditionally as its enforcement mechanism. With default features it also compiles the linked VMM; see `vmm` above.

## Correctness stance

This crate crosses a trust boundary (a signed grant authorizing execution of untrusted content) and is directly consumed outside this repo. See `execution-boundary-adversary` review coverage for RunSpec/RunGrant binding, evidence verification, and backend-parity claims.

## Conformance matrix

One set of shared rows, run against both backends with a real worker and a real guest (bead `ley-line-open-f8ebcf`; Cloister's provider-adoption gate). The rows are written once, in [`tests/conformance/mod.rs`](tests/conformance/mod.rs), and the `conformance_rows!` macro expands them into `#[test]`s for each column, so a column cannot skip a shared vector the other runs. Capability-specific positive rows live in the adapter that can actually enforce them: Graph workspace I/O is a microVM capability, while the shared refusal row proves native fails closed before spawn. The guest is one program, [`tests/conformance/guest.rs`](tests/conformance/guest.rs) (`std` only), compiled into the native column's test binary and as a static Linux program for the microVM column. A started guest proves it is running by dialing the host over its granted channel, and natural completion is the backend's completion condition variable: no row sleeps.

| Column | Binary | Backend and worker | Guest channel | A host path is… |
| --- | --- | --- | --- | --- |
| native nono | `runtime/tests/conformance_matrix.rs` | `NativeWorkerBackend`, `leyline-native-worker` applying Seatbelt or Landlock | §3 `connectLocal` (loopback TCP) | visible, and kernel-denied: `EPERM`/`EACCES`, never `ENOENT` |
| embedded libkrun | `krun-worker/tests/conformance_matrix.rs` | `KrunWorkerBackend`, the real `leyline-krun-worker` booting a guest | §6 `unixSocket.allow` (vsock to a host socket) | absent from the guest's namespace: `ENOENT` |

| Row | Coverage |
| --- | --- |
| `capabilities_and_status_are_read_only` | Capabilities name the tier and its backend id; `status`, `inspect`, `collect`, `cleanup` and `cancel` of an unknown run are the same typed refusal; none of them provisions or writes. |
| `refusals_are_identical_and_precede_backend_work` | Unprovisioned start (`NotProvisioned`), provisioning the other tier, a grant for the other tier (`UnsupportedBackend`), a grant for another confinement policy (`IdentityPolicyMismatch`), an expired grant (`InvalidSpec`), an egress grant and an unenforceable `pids` ceiling (`UnsupportedBackend`), and the channel grant the tier cannot deliver (`InvalidSpec`: §4 `port.bind` on Seatbelt, §6 on Landlock, §3 on the microVM tier). Each leaves the ephemeral root empty. |
| `a_guest_that_exits_zero_is_succeeded_with_a_bound_receipt` | `Running` → `Succeeded`; the receipt binds the spec, grant and attested confinement digest, names the run's rootfs as its one `inputRoots` entry, records the tier's enforcement mechanisms, and its event-log root is the BLAKE3 of the log `inspect` returns; collect is read-only; cleanup closes the lifecycle; the same authority started again is the same run. |
| `a_guest_that_exits_nonzero_is_failed_with_a_content_addressed_detail` | `Failed` with `BackendFailed`; the terminal event carries the BLAKE3 of the typed error. |
| `cancel_ends_a_blocked_guest_and_everything_it_ran` | Both columns: a guest blocked forever is `Running` and has no receipt; `cancel` returns after the worker is reaped, the parked guest's channel has closed, and the run root is gone; the receipt is `Cancelled`; a repeated cancel is idempotent. A killed guest may remain briefly as a pid-1-owned zombie, which cannot execute and is not mistaken for a live escape. |
| `a_killed_worker_is_failed_reaped_and_cleaned` | Crash recovery: SIGKILL the native worker or the VMM. The run ends `Failed`, the worker is reaped, the guest's channel closes (nothing that held it can still execute), the run root is removed, and collect and cleanup still work. On Linux the SIGKILLed guest is reparented to pid 1 and may still be exiting or an unreaped zombie when completion is reported, so the row asserts on the channel, not on signal 0. |
| `undeclared_host_access_and_the_raw_arena_are_unreachable` | The guest reads and writes its own rootfs and reaches its granted channel, and cannot read an existing host file outside the grant, the daemon's arena or living database, or `~/.ssh`, nor reach an ungranted loopback listener (which never sees a connection). |
| `a_workspace_grant_nothing_serves_is_refused_before_spawn` | A Graph workspace grant a backend cannot serve is `WorkspaceUnserved` before anything is spawned, through `start_authorized` (every transport's path) and a direct `start`. |
| `graph_io_goes_through_the_mediated_workspace_share` | MicroVM only: a guest granted a workspace reads a real store's bytes through the share (storefs's `StoreShare`), lists it, writes through it, and the write lands in the store; the store's database is not in the guest's namespace or the listing. Native does not report this as a pass or a skip: `a_workspace_grant_nothing_serves_is_refused_before_spawn` is its explicit fail-closed contract. |

Every guest row also puts `krunvm`, `task` and `go-task` traps first on `PATH` and fails if the execution path ran any of them.

Beside the matrix, `krun-worker/tests/libkrun_oci_rootfs.rs` (bead `ley-line-open-68a55d`) boots a rootfs produced by `import_oci_layout` (`leyline rootfs import-oci`): a static guest packed into a two-layer OCI image is imported, resolved by a `CatalogResolver` from its executable artifact, started through `start_authorized` with the worker under test, and must print its marker on the guest console, exit 0, and get a receipt whose `inputRoots` names the imported digest. One byte changed in a file under that digest in the CAS is refused before the guest boots.

`krun-worker/tests/libkrun_guest_connections.rs` (bead `ley-line-open-be3711`, ADR-0046 Q7) is the declared-connection suite: a §6 grant with `guestPort` reaches a stock `std::net` client and server in the guest as TCP on its loopback, in both directions. It holds the Q7 acceptance tests: dial-out to exactly the declared peer (and nothing once the grant is removed, with a different attested digest); serve reached by the declared peer only; a sweep of every guest loopback port and a set of host vsock ports that finds exactly the declared ones, which match `guest_loopback_channels` computed without a VMM, no route off the guest, and no undeclared VMM socket; a request that cannot widen reach; refusals by name before readiness (unbound peer, over-length socket path, hijacking, off macOS); teardown on cancel; guest datagram sockets refused under both boundaries; and a stability loop (`LEYLINE_CONNECTIONS_RUNS`, default 1) that reports boot stalls separately.

Run it with `task runtime:test`, or one column at a time:

```sh
cargo test -p leyline-runtime --test conformance_matrix            # native nono
LEYLINE_LIBKRUNFW_PATH=/opt/homebrew/lib/libkrunfw.5.dylib \
  cargo test -p leyline-krun-worker --test conformance_matrix      # embedded libkrun
```

Skips are named and are never passes. Without `LEYLINE_LIBKRUNFW_PATH` every libkrun row prints `SKIPPED (NOT a pass)`, and `LEYLINE_REQUIRE_HYPERVISOR=1` turns that into a failure; a host that cannot apply the native sandbox (an outer Seatbelt sandbox, a kernel without Landlock network rules) makes the native guest rows print the same, and `LEYLINE_REQUIRE_SANDBOX=1` turns that into a failure. No hosted CI runner can boot a guest, so the libkrun column runs in the release gate's hypervisor suite (`task release:hypervisor:record`).

Receipt parity across the four surfaces is [`cli-lib/tests/execution_transport_parity.rs`](../cli-lib/tests/execution_transport_parity.rs): one request through the in-process `ExecutionHandler`, the daemon's control socket, a parsed `leyline execution` command line, and MCP `tools/call` gives the same lifecycle and receipt (identical apart from wall-clock fields), and one run read through all four gives byte-identical status, inspection, receipt and errors.
