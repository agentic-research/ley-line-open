# leyline-runtime

Capability-resolved execution lifecycle and isolation backends (`execution/v1`). Product policy is resolved before this crate is called — it accepts content identities and guest-relative names; backend-only host paths are introduced behind trusted resolver boundaries.

## What's here

- **`authorization`** — `AuthorizedExecution`, `EvidenceVerifier` (+ `CasDsseEvidenceVerifier`, `MetadataOnlyEvidenceVerifier`, `RejectUnverifiedEvidence`), `SignedGrant`/`GrantSignature`, `SchemaIntent` — the trust boundary between an execution request and permission to run it. `CasDsseEvidenceVerifier` reports each refusal as an `EvidenceRejection` (`grant-unsigned`, `untrusted-signer`, `signature-invalid`, `evidence-missing`, `evidence-integrity`, …): an `ExecutionError` whose `detail` begins with the reason's stable token, recovered with `EvidenceRejection::of`.
- **`cas_evidence`** — what `leyline execution-daemon --evidence-store DIR --trust-key FILE` installs (bead `ley-line-open-410921`): `CasEvidenceStore`, an `EvidenceStore` over `leyline-core`'s `FsBlobStore` addressed by evidence digests (`blake3-256:<hex>` over the exact envelope bytes); `parse_trust_key`/`load_trust_keys` for operator key files (64 hex characters or a canonical RFC 8410 PEM `PUBLIC KEY`), each named by its ADR-012 canonical kid (SHA-256 over SPKI DER, a key's name, never a content address); and `operator_verifier`, which refuses an empty, malformed or repeated key set and a missing store directory.
- **`artifacts::oci`** — turns a digest-pinned OCI image into the content-addressed rootfs the backends consume (bead `ley-line-open-7736ab`); see "Container images" below.
- **`artifacts::registry`** — pulls a digest-pinned image from a registry into a staged layout and imports it through `artifacts::oci` (bead `ley-line-open-97b636`); see "Registry pulls" below.
- **`cas_volume`** — `CasVolume`, a CAS root on a case-sensitive filesystem (a case-sensitive APFS sparsebundle on macOS, a checked `<state>/cas` on Linux, refused elsewhere), and `default_state_dir` (bead `ley-line-open-ba86d3`); see "Case-sensitive CAS volume" below.
- **`backends`** — isolation backend implementations: `native` (process), `native_backend`, `libkrun` (microVM). `Backend` is the trait each implements; `BackendCapabilities` / `BackendClass` describe what a backend can enforce.
- **`backends::libkrun`** — the microVM tier. `KrunWorkerBackend` supervises the `leyline-krun-worker` binary, which the unpublished [`leyline-krun-worker`](../krun-worker/) crate builds (bead `ley-line-open-395e43`). That crate is the only one that links libkrun, from [`third_party/libkrun`](../../../third_party/README.md) (upstream v1.19.6 plus LLO's patches, ADR-0044); this crate has no libkrun dependency and stays publishable. `worker::prepare` is everything the worker does before the VMM: after refusing reserved environment keys, it commits the confinement manifest (`committed_confinement`, bead `ley-line-open-7a3109`), refusing as `IdentityPolicyMismatch` ("confinement drift") a policy whose digest is not the request's `confinementDigest` (an empty `confinementDigest` is the explicit "no commitment"), then checks the share and the inherited descriptors, compiles the plan, materializes the ephemeral rootfs and applies the committed manifest, and returns a `PreparedRun` (the VM's `KrunConfig`, the share socket, the applied manifest's digest and the inherited descriptors; `PreparedRun::ready` builds the readiness event). The worker crate builds the VM from it through `api::LinkedKrunApi`, attaches the share as a `DynFileSystem` and enters the VM.
- **`backends::libkrun::share`** — a run's workspace as the guest's working tree (ADR-0044 phase C, bead `ley-line-open-f210c2`). A run whose RunGrant carries a `WorkspaceGrant` reaches the backend with `ExecutionRequest.workspaces` (carried by the resolver; the service refuses one that changes them). `ExecutionService::with_workspace_shares` takes the embedder's `WorkspaceShares`. For a run started from a verified grant, the service opens an `FsService` for each granted workspace before it calls the backend, and passes them to `Backend::start` as `ServedWorkspaces` (bead `ley-line-open-1022a8`). Only the service can construct that value, so a backend can serve only shares it was handed, and a request naming workspaces without a verified grant (`ExecutionService::start`, or a direct `Backend::start`) is refused `workspaceUnserved`. The libkrun backend takes the one share it attaches (`ServedWorkspace::attach`), passes one end of a socket pair as `--workspace-share-fd`, and `serve`s the other end. Each share is scoped by its grant, including the grant's `writeScope` (bead `ley-line-open-483134`). The worker checks the descriptor is a socket matching the grant, attaches `ShareFs(RemoteFs)` (`leyline-krun-worker`; libkrun's `DynFileSystem` transcribing each FUSE request onto the wire) under tag `work`, and sets `KRUN_VIRTIOFS_MOUNTS=work:/work` and the working directory `/work`: the guest init (libkrun patch `0005`) mounts the share before the workload runs. The service first asks the backend how many workspaces it serves a run (`Backend::workspace_capacity`, default 0, libkrun 1): more than that, no provider, or a provider refusal refuses the run in the service, with no share opened for a tier that cannot use it and the backend never called. When `start` returns, the service holds the proofs to this run's own shares (each names the run and the whole grant) and to each share still being held; a share kept from another run or let go is refused. The share descriptor is a channel the worker holds outside its `confinement/v1` manifest (nono confines what the process may open, not what it inherits open), so it is declared instead (bead `ley-line-open-b83347`): `worker::declared_descriptors` derives, from the grant and the descriptor number, the descriptors a worker holds beyond its standard streams (the share for a run granted a workspace, none otherwise); the backend spawns the worker through `worker::inherit_only`, which marks every other descriptor it holds close-on-exec in the child (a descriptor the daemon inherited open from its own parent included); the worker lists its open descriptors (`/dev/fd`) before it reads the rootfs and refuses to start holding any it does not declare (`IdentityPolicyMismatch`, naming the descriptors); its readiness event carries the declaration (`inherited`), which the backend refuses unless it equals what it handed the worker; and `BackendRun.attached`, the proof of each share the backend took (a backend cannot write one itself), reaches the receipt, whose `backend.evidence` is the digest of a `BackendEvidenceDocument` (`application/vnd.leyline.execution.backend-evidence+json`, execution/v1 README "Backend evidence") naming the backend and each `WorkerChannel::WorkspaceShare {workspace, graphRoot}`. `WorkspaceGrant.expectedGeneration` is ADR-0041 S1's commit `seq`, which no store records yet, so the store's share refuses a grant whose `expectedGeneration` is nonzero (bead `ley-line-open-39abfa`); the share is pinned by the `graphRoot` check. The wire is one frame per request and reply: two little-endian `u32` lengths, a Cap'n Proto header (`leyline-public-schema`'s `capnp/share.capnp`, bead `ley-line-open-39d3a4`), and READ/WRITE bytes as raw payload. `leyline-storefs`'s `DaemonShares` is the store-backed provider; `rs/ll-open/cli/tests/agent_in_guest.rs` runs an agent in a guest against it (`task runtime:test`, with `LEYLINE_LIBKRUNFW_PATH` and `LEYLINE_GUEST_TOOLS` from `tools/guest_tools.sh`).

- **`backends::libkrun::output`** — what a microVM run printed, kept bounded (bead `ley-line-open-a26ad0`). libkrun connects the guest's standard output to the worker's standard output (its `krun-stdout` console port) and the guest's standard error to the worker's standard error (`krun-stderr`). The worker's standard error also carries the worker's own events and libkrun's diagnostics. The backend keeps the last 16 KiB of the standard output (`GUEST_OUTPUT_TAIL_BYTES`) and the last 8 KiB of the post-readiness standard error (`WORKER_STDERR_TAIL_BYTES`), each with a count of the bytes it dropped, plus the last line there shaped like a `failed` event. Memory per run is fixed however much the guest prints.
  - **On failure.** `BackendRunStatus::Failed` keeps the supervisor's code and `retryable`. A guest can print a line shaped like the worker's `failed` event on the shared stream, so such a line is appended to the detail as unverified text, never adopted (test `a_guest_cannot_classify_its_own_failure`). Both tails follow, under `--- guest console ---` and `--- guest stderr and worker diagnostics ---` headings.
  - **The typed result.** The one shape for guest output is `GuestOutput { stdout_tail, stdout_dropped_bytes, stderr_tail, stderr_dropped_bytes, untrusted: true, reported_failure }` (`leyline_runtime::GuestOutput`, serialized camelCase). A finished or failed run's output comes with its status as `RunOutcome { status, output }`: `KrunWorkerBackend::wait_for_outcome(run_id)` waits for it, and `Backend::poll_outcome(run_id)` consumes it. The default implementation is `poll` with `output: None`. `poll` and `wait_for_completion` still return the status alone. The daemon socket does not carry it yet (bead `ley-line-open-eea8e1`).
  - **While the run is active.** `Backend::output(run_id)` returns the tails, and `KrunWorkerBackend::wait_for_output(run_id, until, timeout)` waits, by event, for a condition on them, for example a server's "listening" line.
  - **Where the bytes go: deny by default.** They reach only the in-process embedder that started the run. `ExecutionService` records a failure's detail only as the BLAKE3 digest in the terminal event's `detailDigest`, so the event log commits to the output without carrying it. Nothing writes the output to disk, logs it, or sends it over the daemon's wire.
  - **Trust.** The bytes are the workload's own, untrusted, and may hold anything it printed; LLO adds nothing to them. Invalid UTF-8 and control characters other than newline and tab become U+FFFD, so a terminal showing a detail cannot be driven by the guest's escape sequences. That includes a reported event's decoded detail. The section headings are framing, not authority: guest bytes keep their newlines and can imitate a heading or the "(unverified)" line. A classification an embedder can trust needs a worker-event channel the guest cannot write, which stderr is not. `wait_for_output`'s condition runs under the run's capture lock, so it must not read the same run's output again.
  - **`outputBytes` is unaffected.** The tail is a diagnostic, not the `outputBytes` ceiling, which stays unenforced and refused.

## Container images

An OCI image is a build input and distribution format here, not an isolation boundary. libkrun (or, on the native tier, nono) is the boundary; the image only supplies the files a run's rootfs holds. Docker, Buildah, Podman, skopeo and crane are optional ingestion adapters: any of them may write the [OCI image layout](https://github.com/opencontainers/image-spec/blob/v1.1.0/image-layout.md) an import reads, and none is needed to import or run it. A Zarf package's `images/` directory is such a layout (oras-go writes it) and imports as one. An image can also be pulled by digest from a registry (see "Registry pulls"). Execution never contacts a container daemon and never shells out to krunvm.

`artifacts::oci::import_oci_layout`, and the `leyline rootfs import-oci --layout DIR --image sha256:<hex> --cas-root DIR [--symlinks refuse|resolve]` command over it, publish the image's root filesystem as `<cas-root>/<blake3 hex>/` with its `rootfs.manifest.json`. The digest is the existing rootfs identity: BLAKE3 over the manifest's exact bytes, which `DirectoryRootfsResolver` verifies on every resolve, and the `rootfs` an execution catalog entry names. The command prints one JSON document: `rootfs` (that digest, as `{"algorithm":"blake3-256","value":…}`), `image` (the pinned reference, the manifest and config digests, and the platform: OCI SHA-256 provenance, never compared with the rootfs digest), counts, and `imageConfig` (the config's entrypoint, cmd, env, working directory and user, advisory for whoever writes the catalog), and four lists of what the import dropped instead of writing (each empty when nothing was): `specialEntriesDropped` (`{layer, path, kind}`, kind `char`, `block` or `fifo`), `linksDroppedKernelMount` and `linksDroppedDangling` (`{path, target}`), and `unreadableFilesDropped` (`{path, mode}`).

The import's contract, each clause tested in [`tests/oci_rootfs.rs`](tests/oci_rootfs.rs):

| Clause | Behavior |
| --- | --- |
| Pinned input | `sha256:<hex>` or `name@sha256:<hex>` of an index or manifest. A tag is refused; `index.json`, whose tags are mutable, is never read. |
| Authentication | Every blob must be a regular file, hash to its descriptor digest and match its size before it is parsed; layers are verified into owner-only staging and parsed from there. Each layer's whole uncompressed stream (every gzip member) must hash to its config `diff_id`. |
| Bounds | `max_rootfs_bytes` (16 GiB from the CLI) bounds the decompressed bytes of all layers, headers and long-name metadata included, and separately the bytes written. Paths and link targets over 4096 bytes are refused. |
| Platform | An index yields the one entry for the requested platform (`arm64` without a variant is `arm64/v8`); none or several is an error. The config must agree. The CLI always requests this host's Linux platform, the only one libkrun can boot. |
| Layers | Applied in order to an in-memory tree. `.wh.<name>` and `.wh..wh..opq` remove lower-layer entries only. Gzip and uncompressed layers are read; zstd is refused. |
| Modes | A file's permission bits are kept. Setuid, setgid and sticky bits are cleared and counted. A file its owner cannot read is dropped (see "Dropped entries"). Directory modes, empty directories, ownership, timestamps and extended attributes are not in rootfs manifest v1, so none is carried: directories are written `0755` only where a file needs one, so one digest names one tree on disk. A directory entry its owner cannot both read and search (mode without `0500`) is therefore refused: written `0755` it would expose what it hides. The guest init creates `/dev`, `/proc` and `/sys` itself. |
| Links | Rootfs manifest v1 has no link entries. `--symlinks refuse` (the default) names the first link; `resolve` replaces each with a copy of the file or directory it resolves to inside the image (absolute targets mean the image root). Under `resolve`, a link into a kernel mount and a dangling link are dropped (see "Dropped entries"); a link that reaches `/work`, a loop, a `..` above the image root (also in the part of a target after a missing component), a target that continues through a regular file, an empty target and a directory link containing itself are refused. Hard links become a second regular file. |
| Paths | An absolute entry name or hard-link target is read from the image root, as containerd and Docker read it: Nix `dockerTools` layers name `/nix/store/...`, and `/nix/store/x` is `nix/store/x` (bead `ley-line-open-cffbb5`). The traversal rules then apply to it unchanged. `..` (in an absolute name too), entries under a regular file or through a link, device nodes and FIFOs outside the kernel mounts, and an image-root `rootfs.manifest.json` are refused. No image path reaches the host filesystem until the finished tree is written beneath staging inside the CAS root; extracted contents wait there under their BLAKE3 names. |
| Identity | Files are listed in path order with fixed field order, so the same image content has the same rootfs digest whatever its archive order, host or run. A dropped entry is not in the manifest: an image's digest is that of the same image with its dropped entries, and whatever they replaced in lower layers, removed. The drop lists in the JSON are per-import provenance like `image`, not part of the identity: two images with one digest can report different drops. These rules changed what some images import as (`changes/ley-line-open-fe3d26.md` lists the cases); an image with nothing to drop or newly refuse keeps its digest. |
| Name collisions | Before any layer is read, the import probes once how the CAS root's filesystem compares names (two empty files in a private directory it removes) and reports it as `casRootFilesystem` (`{caseSensitive, normalizationSensitive}`). Before any image path is written, two paths of the finished tree that the filesystem would store as one name (`usr/share/perl/Pod` and `usr/share/perl/pod` on a case-insensitive root; the NFC and NFD spellings of a name on any APFS volume, case-sensitive ones included) refuse the import with `PathCollision`, naming both paths and the CAS root's case or normalization insensitivity; the CAS root is left as it was. They are never merged, renamed or dropped: a merged tree is a different filesystem from the image. An image with no such pair imports on any root to the same digest. See "Case-sensitive CAS volume" below. |
| Publication | The staged tree is verified against its own manifest and renamed into place. An existing entry is reused only if its files verify and its directories are exactly the ones the import wrote, all `0755`; it is never replaced. Files are not fsynced before the rename. The resolver checks files only, since manifest v1 names no directory, so it accepts a CAS entry whatever its directories; what reaches the guest is the per-run copy, which `materialize_ephemeral_rootfs` builds from the manifest, not from the entry: the listed files and the directories they imply, every directory (the root included) at `0755`, nothing else. A directory someone widened or planted in the CAS entry never reaches the guest, a file in an unimplied directory is refused as undeclared, and `verify_ephemeral_rootfs` refuses, before VM entry, a copy whose directories are not exactly that set at `0755`. So one rootfs digest names one guest tree whoever wrote the entry (bead `ley-line-open-38ff59`). |

### Registry pulls

`artifacts::registry::pull_oci_image`, and `leyline rootfs import-oci --from-registry [registry/]repository@sha256:<hex> --cas-root DIR [--symlinks refuse|resolve]` over it (bead `ley-line-open-97b636`), pull one digest-pinned image over the [OCI distribution API](https://github.com/opencontainers/distribution-spec/blob/v1.1.0/spec.md) and import it. The pull writes what it fetches into a staged OCI image layout, owner-only, inside the CAS root, and runs `import_oci_layout` on that layout unchanged: one verifier, so a pull and a `--layout` import of the same digest publish the same rootfs digest and print the same JSON. `--layout` stays the offline and air-gapped input. Each clause is tested against an in-process registry in [`tests/oci_registry_pull.rs`](tests/oci_registry_pull.rs):

| Clause | Behavior |
| --- | --- |
| Pinned input | `[registry/]repository@sha256:<hex>` of an index or manifest. A tag, alone or beside a digest (`name:tag@sha256:…`), is refused; so is a bare digest, which names no repository. A name without a registry is Docker Hub's (`registry-1.docker.io`, a one-component name in `library/`). |
| What is fetched | The pinned document, the one manifest the platform rule above selects from an index, that manifest's config and its layers; nothing else. An index entry's digest must be well formed before it is requested, and the manifest must pass the import's own manifest check (image manifest, container-image config of at most 4 MiB, every layer of a readable type) before any blob is requested. A blob a manifest lists twice is fetched once. |
| Verification | Every document and blob passes the layout import's own digest and descriptor-size check before it is parsed or kept, and a blob is read at most one byte past its descriptor's size. The import then verifies the staged layout as it verifies any layout (digests again, `diff_id`s, the decompressed-size bound). |
| Transport | HTTPS only: the first request, a token realm and every redirect. Plain HTTP is refused unless `--insecure-plain-http-registry HOST:PORT` (`RegistryPull::insecure_plain_http`) names that exact authority, which must be a loopback address (`127.0.0.1:<port>`, `[::1]:<port>`); it exists for a local test registry. A token realm or redirect that resolves to a loopback, private (RFC 1918, unique-local), link-local, CGNAT or otherwise non-public address is refused before any connection is opened (`NonPublicDestination`, naming the address), unless it is the registry the reference names or the exact loopback authority the opt-in names; the check is on the addresses the connection would use, so a name that resolves to one is refused like a literal. The registry itself may be on a private network, but one that has resolved to public addresses may not resolve to a non-public one later in the same pull (bead `ley-line-open-b1c18d`). No proxy from the environment is used. |
| Authentication | Anonymous only: a `401` with `WWW-Authenticate: Bearer realm=…` is answered with one anonymous token for `repository:<name>:pull` (ghcr.io, Docker Hub), sent to the registry's own URLs and never on a redirect, so a CDN receives none. A `Basic` challenge, a challenge without a realm, and a token the registry still refuses are errors. No credential is read from anywhere, and the token never appears in an error; an error names a redirect target without its query. |
| Bounds | `RegistryLimits`: `max_download_bytes` (16 GiB by default) over everything downloaded, the documents counted as they arrive and the config and layers by their descriptors' sizes before any of them is requested; `max_redirects` (5) per request; `connect_timeout` (30 s); `response_timeout` (60 s) as the longest a body may go without a byte; every request's headers, connecting and the TLS handshake included, by `2 × connect_timeout + response_timeout`, enforced on every read of the connection, so a server that trickles header bytes is cut there rather than by the 64 KiB header limit; and each request's deadline, `response_timeout` plus its body's size at `min_bytes_per_second` (128 KiB/s), so a large layer may take as long as its size needs and a slow drip is still cut off. |
| Staging | The staged layout and the import's own staging are inside the CAS root and removed whatever the outcome; a refused pull leaves the CAS root as it was. A layer is on disk twice while it is imported (the staged blob and the import's verified copy). |

Not in v1: credentials (no secret may reach argv or logs, so any design takes them from a file or the environment), proxies, and non-loopback plain-HTTP registries.

### Dropped entries

Deny means never materializing what the rootfs cannot carry faithfully. For the classes below the import drops the entry instead of refusing the whole image, writes nothing in its place, and names it in the JSON; each bullet states what a guest can still observe of the difference, so a consumer can judge it. Each rule is checkable against libkrun's guest init, [`rs/third_party/libkrun/src/init_blob/init/init.c`](../../third_party/libkrun/src/init_blob/init/init.c) (upstream v1.19.6 with LLO's patches applied):

- **The kernel-mounted set is `dev`, `proc`, `sys` and `tmp`.** `mount_filesystems` (init.c) mounts devtmpfs on `/dev`, proc on `/proc` and sysfs on `/sys`, then cgroup2 on `/sys/fs/cgroup`, devpts on `/dev/pts` and tmpfs on `/dev/shm`, which are all beneath the first three. Since LLO patch `0012` (bead `ley-line-open-db5899`) it also calls `mount_tmp`, which mounts a tmpfs on `/tmp`. Each mount either succeeds or makes init exit before the workload runs; the first three also accept a mount already there (`EBUSY`).
  - **`/tmp` on every non-TDX boot.** The tmpfs is mode 1777, `nosuid` and `nodev`, and is sized at 25 % of the guest's RAM (`TMP_SIZE_PERCENT`). A write past that bound fails `ENOSPC`. `/dev/shm` keeps the kernel's default size, so the two tmpfs mounts together can pin three quarters of guest RAM; neither can exceed the RAM the grant sized the VM at. Init creates the mount point when the rootfs has none, and mounts only over a real directory, so a `/tmp` that is a link or a file stops the guest. An image with a regular file at `tmp` (or at `dev`, `proc` or `sys`) is refused at import (`KernelMountPointNotDirectory`, below; bead `ley-line-open-2aa5d3`). Creating the mount point matters because a rootfs never carries an empty directory, so an image's empty `tmp/` does not survive import.
  - **Nothing written there persists.** The tmpfs is memory-backed and per-boot: nothing written reaches the host or outlives the guest.
  - **What an image holds under `tmp/` is shadowed.** The workload never sees it, so `tmp/` follows the same drop rules as the other three: devices and FIFOs beneath it are dropped, and links into it are dropped under `--symlinks resolve`.
  - **Regular files under `tmp/` are still imported**, as they are under `dev/`, `proc/` and `sys/`. They count toward the rootfs digest but are invisible in the guest. Dropping them would change the digest of every image that ships a file there, for no difference the workload can observe.
  - TDX builds keep upstream's `/tmp` handling (an ext4 root volume) and are not built by LLO.
  - Function names are the stable reference; line numbers move with the patch series.
- **Device nodes and FIFOs** (`specialEntriesDropped`). One strictly beneath `dev/`, `proc/`, `sys/` or `tmp/` is dropped: the kernel filesystem mounted over its directory hides it. It replaces whatever a lower layer, or an earlier entry of its own layer, had at its path, as any layered filesystem does. One anywhere else, or at the mount point itself, or beneath a `dev` that is a link, is refused by name, as is a hard link to a dropped one (its target is gone). The list holds each entry as it was dropped, in layer and archive order, so a later entry of the same layer may still have written a regular file at that path. LLO's own v0.27.0 image ships five such devices under `dev/`.
- **Regular files their owner cannot read** (`unreadableFilesDropped`, e.g. `etc/shadow` at `0000`). No unprivileged reader can read one: not the import's verifier, not `DirectoryRootfsResolver`, and not the guest, whose virtio-fs server runs as the same unprivileged host user. It is never written at a changed mode, so credential material like `shadow` stays out of every rootfs. The difference a guest can observe: `stat` reports `ENOENT` instead of the file, and `open` fails `ENOENT` instead of `EACCES`. A hard link to one, or a resolved link to one, is dropped at its own path too (`symlinksResolved` still counts that link). On a host where the worker runs as root such a file would be readable; it is dropped all the same, never widened. An unreadable or unsearchable directory, and a file that cannot be read for any other reason, are still refused.
- **Links into a kernel mount, under `--symlinks resolve`** (`linksDroppedKernelMount`, e.g. `etc/mtab -> /proc/mounts`). A link whose resolution goes beneath `dev`, `proc`, `sys` or `tmp`, or ends at one of them, directly or through other links, is dropped: beneath the mount point the guest kernel and its own links (`/proc/self/root`) decide what the walk reaches, so no bytes the image holds under those directories stand in for it, even where the kernel's answer would lead back into the image. A `..` straight back out of the mount point (`/dev/../etc/f`) is followed, as the guest follows it, and the link is copied. The difference: the guest sees no link at that path, so `open("/etc/mtab")` fails `ENOENT` where the real link would have reached the kernel's mount table. This is a fidelity loss, not an exposure: nothing is written. Before this rule, a link into one of these directories whose target the image held (`cpuinfo -> /proc/cpuinfo` beside an image file `proc/cpuinfo`) was copied from the image's bytes; it is now dropped.
- **Dangling links, under `--symlinks resolve`** (`linksDroppedDangling`, e.g. `usr/share/zoneinfo/localtime -> /etc/localtime` with no `/etc/localtime`, or a Debian doc link left by a `dpkg` path-exclude). At boot, `open` through such a link fails `ENOENT` in the guest, as it does on the absent path. The differences: `readlink` and `lstat` report `ENOENT` instead of the link; a write that would have created the target through the link creates a file at the link's own path instead; and if the workload later creates the target (the guest's root is a writable per-run copy), the real link would reach it and the absent one does not. A link inside a directory copied through a directory link is listed at each path it would have been written.
- **Links that reach `/work` are refused**, whether or not the image holds `work/`: the libkrun worker has init mount a granted workspace there (`backends::libkrun::worker::WORKSPACE_DIR`; init.c `mount_virtiofs_list`, called from `main`), so neither the image's bytes nor their absence decides what such a link reaches.
- **Still refused by name**: a loop (over 40 links), a `..` above the image root anywhere in the target (after a missing component or a kernel mount point included), a target that continues through a regular file, an empty target, and a directory link that contains itself. The default `--symlinks refuse` refuses the first link of any kind, as before.
- **A regular file at a kernel mount point is refused by name** (`KernelMountPointNotDirectory`; bead `ley-line-open-2aa5d3`), never dropped: a file `dev`, `proc`, `sys` or `tmp`, or under `--symlinks resolve` a link there that resolves to a regular file (`tmp -> /etc/hostname`). Init mounts a filesystem over each and `mount(2)` cannot mount over a file, so such an image would import and then stop at boot. A device or FIFO at the mount point is refused as above; a directory there imports.

The citations are for the libkrun tier, whose guest runs that init. The native tier runs the workload with the rootfs as its working directory and the host's own `/dev`, `/proc` and `/sys`; for it, a dropped device or link is one rootfs manifest v1 could never have carried, and a dropped unreadable file is one its verifier could never have read.

Where each kind of test runs: the importer, the resolver and the conformance rows that need no guest run anywhere, including in a container; a real guest needs a hypervisor, so macOS Hypervisor.framework tests run on a macOS host and Linux KVM tests on a host or runner given `/dev/kvm` (the libkrun column of the conformance matrix, below). Booting an imported rootfs in a guest is part of the hypervisor suite: `krun-worker/tests/libkrun_oci_rootfs.rs` (below).

### Case-sensitive CAS volume

`cas_volume` (bead `ley-line-open-ba86d3`) supplies a CAS root on a case-sensitive filesystem, for images that need one. Design is host-agnostic; macOS ships first, and every other host refuses by name.

| Host | `CasVolume::provision` |
| --- | --- |
| macOS | Creates (once) a grow-on-demand, case-sensitive APFS sparsebundle with `/usr/bin/hdiutil create -type SPARSEBUNDLE -fs "Case-sensitive APFS"`, under a private name renamed into place, and attaches it with `hdiutil attach -nobrowse -noautoopen -owners on -mountpoint`. Runs as the calling user: `hdiutil` creates and attaches a user-owned image without privilege, and the mount is `nodev,nosuid`. No network, no secret. |
| Linux | Makes no volume: creates `<state>/cas` if missing, probes it, and succeeds on a case-sensitive filesystem; otherwise refuses by name (`CaseInsensitive`, e.g. a casefolded directory or vfat). |
| Other | Refused by name (`UnsupportedHost`). |

Paths are fixed beneath the state directory `<state>`: `$LEYLINE_STATE_DIR`, else `$XDG_STATE_HOME/leyline`, else `$HOME/.local/state/leyline` (`default_state_dir`).

```text
<state>/cas-volume/                  owner-only (0700)
<state>/cas-volume/cas.sparsebundle  the image
<state>/cas-volume/mnt/              its mountpoint
<state>/cas-volume/mnt/cas/          the CAS root (macOS)
<state>/cas-volume/mnt/runs/         the default run root (macOS)
<state>/cas/                         the CAS root (Linux)
<state>/runs/                        the default run root (Linux)
```

- **Run root** (bead `ley-line-open-741388`). Each run's rootfs is copied beneath the run root, so it must be case-sensitive like the CAS root: an image with `usr/share/perl/Pod/` beside `usr/share/perl/pod/` imports into the volume, but its copy on default APFS fails "File exists". With `--cas-volume`, `leyline execution-daemon` therefore defaults the run root onto the volume, beside `cas/`, and provisioning creates it. A `--run-root` given beside a volume must probe case-sensitive. One off the volume is checked when the daemon starts, which refuses it with `RunRootCaseInsensitive`, naming the run root and the CAS root. One on the macOS mountpoint, as Cloister passes, exists only once the volume is attached, so every provision checks it. A `--run-root` with a `..` component, or inside or holding the CAS root, is refused outright. Both the native and the microVM tier materialize beneath it. On the volume, runs and the CAS share the sparsebundle's size cap: a guest's writes, and whatever a crashed run leaves behind, count against it, and space freed inside the image returns to the host only after `hdiutil compact`.

- **Returned path.** `ProvisionedCas.cas_root` is the CAS root: the `--cas-root` of `leyline rootfs import-oci`, and what Cloister sets `CLOISTER_CAS_ROOT` to. The result also names the image, the mountpoint, whether this call created or attached it, the size cap and the probed `filesystem`.
- **Idempotent.** An existing image is attached, an attached one is reused, and neither is recreated or reformatted. A volume that is mounted but probes case-insensitive is refused, as is a `cas/` that is a link or not on the attached volume. The volume is not otherwise matched to its image: `<state>/cas-volume` is owner-only, and every rootfs is digest-verified on resolve.
- **Size cap.** `DEFAULT_SIZE_CAP_BYTES` (64 GiB) is the image's logical maximum, set when it is created (at least 1 GiB); the image file holds only what is written. A cap passed for an existing image is not applied: resize it with `hdiutil resize -size <new> <state>/cas-volume/cas.sparsebundle` while detached. The image does not shrink by itself (`hdiutil compact`, while detached, reclaims freed space).
- **Start.** `CasVolume::attach_existing` re-attaches a volume an earlier provision created and never creates one; a provider or daemon calls it when it starts. `leyline execution-daemon --cas-volume [STATE_DIR] [--cas-volume-size-cap-gib N]` does, instead of `--cas-root`; its `llo_execution_provision` provisions the volume before the backend's readiness check and reports the CAS root as `ProvisionOutput.casRoot` (with `--cas-root` it reports that directory).
- **Detach and cleanup.** Nothing detaches the volume implicitly, daemon exit included: it stays attached until `CasVolume::detach`, `hdiutil detach <state>/cas-volume/mnt`, logout or reboot. A detach fails, and leaves it attached, while a file in it is open (a running VM's rootfs copy, an import). Removing it is the operator's: detach, then delete `cas.sparsebundle`. Every rootfs in it can be re-imported.
- **CLI.** `leyline rootfs provision-cas [--state-dir DIR] [--size-cap-gib N]` provisions and prints `ProvisionedCas` as JSON (`casRoot`, `mountpoint`, `image`, `created`, `attached`, `sizeCapBytes`, `filesystem`).

`hdiutil` on macOS 26 and later prints a deprecation warning pointing at `diskutil image`; it still performs these operations.

Tests: the logic of every host is unit-tested with a fake disk-image tool (`src/cas_volume.rs`); `tests/cas_volume.rs` and `rs/ll-open/cli/tests/execution_cas_volume.rs` run the real tool on macOS with `LEYLINE_CAS_VOLUME_TESTS=1` (each detaches and deletes what it created) and always run on Linux; with `LEYLINE_OCI_ACCEPTANCE_DIR` also set, the mache and rosary images import into a provisioned volume with their recorded digests.

## Conformance matrix

One set of shared rows, run against both backends with a real worker and a real guest (bead `ley-line-open-f8ebcf`; Cloister's provider-adoption gate). The rows are written once, in [`tests/conformance/mod.rs`](tests/conformance/mod.rs), and the `conformance_rows!` macro expands them into `#[test]`s for each column, so a column cannot skip a shared vector the other runs. Capability-specific positive rows live in the adapter that can actually enforce them: Graph workspace I/O is a microVM capability, while the shared refusal row proves native fails closed before spawn. The guest is one program, [`tests/conformance/guest.rs`](tests/conformance/guest.rs) (`std` only), compiled into the native column's test binary and as a static Linux program for the microVM column. A started guest proves it is running by dialing the host over its granted channel, and natural completion is the backend's completion condition variable: no row sleeps.

Beside the matrix, `krun-worker/tests/libkrun_oci_rootfs.rs` (bead `ley-line-open-68a55d`) boots a rootfs produced by `import_oci_layout` (`leyline rootfs import-oci`): a static guest packed into a two-layer OCI image is imported, resolved by a `CatalogResolver` from its executable artifact, started through `start_authorized` with the worker under test, and must print its marker on the guest console, exit 0, and get a receipt whose `inputRoots` names the imported digest. One byte changed in a file under that digest in the CAS is refused before the guest boots.

`krun-worker/tests/libkrun_guest_connections.rs` (bead `ley-line-open-be3711`, ADR-0046 Q7) is the declared-connection suite: a §6 grant with `guestPort` reaches a stock `std::net` client and server in the guest as TCP on its loopback, in both directions. It holds the Q7 acceptance tests: dial-out to exactly the declared peer (and nothing once the grant is removed, with a different attested digest); serve reached by the declared peer only; a sweep of every guest loopback port and a set of host vsock ports that finds exactly the declared ones, which match `guest_loopback_channels` computed without a VMM, no route off the guest, and no undeclared VMM socket; a request that cannot widen reach; refusals by name before readiness (unbound peer, over-length socket path, hijacking, off macOS); teardown on cancel; guest datagram sockets refused under both boundaries; and a stability loop (`LEYLINE_CONNECTIONS_RUNS`, default 1) that reports boot stalls separately.

A serve channel's peer may connect before the workload listens (bead `ley-line-open-a915e3`). By then the connection is established: the VMM accepted it and the guest kernel completed the vsock leg. So the guest relay holds it and retries the workload's `127.0.0.1:<guestPort>`. Only `ECONNREFUSED` (nothing listening) is retried and bounded. Once something listens, a handshake that its full accept queue delays is waited for as a blocking `connect` would wait for it. Waits back off from 5 ms, doubling, to 200 ms, and the whole hold is bounded by `SERVE_HOLD_MS`, 10 s: the MySQL client library's default `connect_timeout`, so a stock client still waiting sees the outcome no later than its own timeout would end the wait. That bound caps the work at about 60 connect attempts. Every wait is a `poll(2)` that ends at once if the peer hangs up. Each connection is held in its own process, so a held connection never delays another one on the same channel or any other.

A client's first connection therefore works once the server is up, host to VM and VM to VM (B's dial path equal to A's bind path, A started first). When the bound passes, or the workload never listens or has died, the relay closes the held connection. **Platform limit:** on macOS the host end of a serve channel is a UNIX stream socket, and its peer sees only end-of-file (`recv` 0, then `EPIPE` on `send`), never `ECONNRESET`, however the other end closes. `SO_LINGER {1,0}`, unread data and `SHUT_RD` all measure the same, and the vsock leg carries no reset either. So at the bound the peer reads end-of-file without a byte, distinguishable from an immediate hang-up only by the hold. The only refusal a UNIX socket can express is `ECONNREFUSED` at `connect`, which needs the host path not to listen while the workload does not: bead `ley-line-open-b00ae3`. The suite holds the four cases: late workload and never-listening workload, each host to VM and VM to VM. It also holds a fifth: a held connection whose peer hangs up is released at once, not at the bound. Held connections are not capped in number (bead `ley-line-open-bb3395`).

Run it with `task runtime:test`, or one column at a time:

```sh
cargo test -p leyline-runtime --test conformance_matrix            # native nono
LEYLINE_LIBKRUNFW_PATH=/opt/homebrew/lib/libkrunfw.5.dylib \
  cargo test -p leyline-krun-worker --test conformance_matrix      # embedded libkrun
```

Skips are named and are never passes. Without `LEYLINE_LIBKRUNFW_PATH` every libkrun row prints `SKIPPED (NOT a pass)`, and `LEYLINE_REQUIRE_HYPERVISOR=1` turns that into a failure; a host that cannot apply the native sandbox (an outer Seatbelt sandbox, a kernel without Landlock network rules) makes the native guest rows print the same, and `LEYLINE_REQUIRE_SANDBOX=1` turns that into a failure. No hosted CI runner can boot a guest, so the libkrun column runs in the release gate's hypervisor suite (`task release:hypervisor:record`).

Receipt parity across the four surfaces is [`cli-lib/tests/execution_transport_parity.rs`](../cli-lib/tests/execution_transport_parity.rs): one request through the in-process `ExecutionHandler`, the daemon's control socket, a parsed `leyline execution` command line, and MCP `tools/call` gives the same lifecycle and receipt (identical apart from wall-clock fields), and one run read through all four gives byte-identical status, inspection, receipt and errors.
